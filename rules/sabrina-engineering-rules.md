# Sabrina Ramonov Engineering & AI Coding Rules

> Sourced from Sabrina Ramonov (`SabrinaRamonov/ai-coding-rules`)  
> Strict pragmatic standards for developer velocity, type safety, and clean architecture.

---

## 1. Before Coding

- **BP-1 (MUST)** Ask the user clarifying questions if requirements or domain logic have any ambiguity.
- **BP-2 (SHOULD)** Draft and confirm an approach before writing complex code.
- **BP-3 (SHOULD)** If $\ge 2$ viable approaches exist, list clear pros, cons, and tradeoffs.

---

## 2. While Coding

- **C-1 (MUST)** Follow Test-Driven Development (TDD): scaffold stub $\rightarrow$ write failing test $\rightarrow$ implement minimum passing code $\rightarrow$ refactor.
- **C-2 (MUST)** Name functions and variables strictly using existing domain vocabulary for consistency.
- **C-3 (SHOULD NOT)** Introduce classes when small, pure, testable functions suffice.
- **C-4 (SHOULD)** Prefer simple, composable, testable functions.
- **C-5 (MUST)** Prefer branded types for entity IDs to prevent accidental ID mixing:
  ```ts
  type UserId = Brand<string, 'UserId'>   // ✅ Good
  type UserId = string                    // ❌ Bad
  ```
- **C-6 (MUST)** Use `import type { ... }` for type-only imports to preserve clean bundle tree-shaking.
- **C-7 (SHOULD NOT)** Add unnecessary comments; write self-explanatory code with meaningful naming. Only comment critical non-obvious caveats.
- **C-8 (SHOULD)** Default to `type`; use `interface` only when declaration merging or object-oriented polymorphism is required.
- **C-9 (SHOULD NOT)** Extract a new function unless it will be reused elsewhere, is the only way to unit-test opaque logic, or drastically improves readability.

---

## 3. Testing Standards

- **T-1 (MUST)** Co-locate unit tests alongside source files using `*.spec.ts` (or `*.test.ts`).
- **T-2 (MUST)** For any API or endpoint change, add/extend integration tests in `test/*.spec.ts`.
- **T-3 (MUST)** ALWAYS cleanly separate pure-logic unit tests from database-touching integration tests.
- **T-4 (SHOULD)** Prefer integration tests over heavy, brittle mocking.
- **T-5 (SHOULD)** Unit-test complex algorithms and edge cases thoroughly.
- **T-6 (SHOULD)** Test the entire structure in a single comprehensive assertion when possible:
  ```ts
  expect(result).toEqual([expectedValue]); // ✅ Good

  expect(result).toHaveLength(1);         // ❌ Bad
  expect(result[0]).toBe(expectedValue);   // ❌ Bad
  ```

---

## 4. Database & State Management

- **D-1 (MUST)** Type database helpers as `KyselyDatabase | Transaction<Database>` (or generic client/transaction union) so functions work seamlessly inside or outside transactions.
- **D-2 (SHOULD)** Override incorrect autogenerated types in dedicated `db-types.override.ts` files instead of modifying generated migration files directly.
